# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project identity

A Korean-language text RPG (Flask backend + vanilla-JS frontend) whose actual purpose, per [PROJECT_GOAL.md](PROJECT_GOAL.md), is a **simulation-driven balance-tuning and player-behavior-analysis system** — the game is the data-collection vehicle, not the end goal. Battle math lives in a single engine (`ai/battle/`) shared by real Flask battles and headless Monte Carlo simulation, specifically so balance conclusions drawn from simulation transfer to live play. Keep that sharing intact when touching battle mechanics — don't fork logic between "real" and "simulated" paths.

`README.md`'s "실행"/"검증" commands (`python3 Main.py`, `ai.Battle_Engine` imports) describe an earlier pre-Flask CLI layout — `Main.py` no longer exists. Use the commands below instead.

## Commands

Run the dev server:
```bash
python3 App.py                       # http://localhost:5000, FLASK_DEBUG=0 by default (see .env.example)
```

Production-like run (what Render actually starts, `Procfile`):
```bash
gunicorn App:app --workers 1 --threads 8 --worker-class gthread --bind 0.0.0.0:$PORT
```
`--workers` must stay at 1 — `BattleSession`/`BalanceHook` (the `battle`/`hook` keys in a session dict) are in-memory only and never persisted (see Architecture below); a second worker process would not see them.

Tests are standalone scripts, not pytest — no test runner config exists. Run one file directly from the project root:
```bash
python3 TestFile/test_element_fix.py     # single test file
for f in TestFile/test_*.py; do python3 "$f"; done   # full quick suite
```
Each prints `✅`/`❌` per assertion and exits non-zero on failure. `TestFile/montecarlo.py` is a long-running balance simulation (many thousands of simulated battles), not a pass/fail regression test — don't include it in a "run the suite" pass.

Local DB is SQLite at `ai_rpg.db` (gitignored, auto-created by `init_db()` on boot). Delete the file to reset local state; schema changes need no migration tool since `init_db()` just calls `Base.metadata.create_all()`.

## Architecture

### Backend layering (bottom to top)
- `DB/` — SQLAlchemy models (`Models.py`) + `get_session()` context manager (auto commit/rollback/close). `DATABASE_URL` env var switches SQLite → Postgres with no code change.
- `game/` — domain models: `Player_Class.py`, `Enemy_Class.py`, `Inventory.py`, `Lv.py` (leveling), `Skill.py`, `Rewards.py`, `Map.py` (node-map generation/spawn tables).
- `ai/battle/` — the stateless battle engine (`Entity`, `ATB`, `Actions`, `Elements`, `Damage`, `Skills`, `Items`, `Engine`, `MonsterKit`, `EliteKit`). Pure calculation: no Flask, no session state. Its `__init__.py` docstring states the internal dependency layering — read it before adding a new module here.
- `ai/Battlesession.py` + `ai/battle_session/` — the stateful, Flask-facing wrapper. `BattleSession` (in `Battlesession.py`) is composed from mixins in the `battle_session/` package (`Targeting`, `ATB_Flow`, `Rewards`, `Player_Actions`, `Enemy_Actions`, `Elite_Actions`, `State`, `Battle_Log`) — `step(action)` is the only entry point routes call. When changing turn/reward/logging behavior, find the right mixin rather than adding to `Battlesession.py` itself.
- `ai/Auto_AI.py` — `PlayerAI`/`EnemyAI` decision logic (skill/target selection), used by both live battles and simulation.
- `app/` — Flask blueprints, one per feature: `Game.py` (new game/status/skills/items), `Battle.py`, `Inventory.py`, `Rest.py`, `Ranking.py`, `Map.py` (node-map traversal). `Shared.py` holds cross-blueprint state/helpers — see session persistence below. `Master.py` (local-only debug shortcuts — see below) is registered conditionally, not in this always-on list. Blueprints are imported in `app/__init__.py` by capitalized filename (`from .Game import game_bp`, matching the committed filename case) — this matters because deployment runs on case-sensitive Linux while local dev is often case-insensitive macOS; a filename/import-case mismatch works locally and 404s in production.
- `core/` — `Balance_Hook.py` (background simulation feeding live balance decisions), `RedisCache.py` (thin optional cache — see "Redis fallback" below).

### Session persistence (3-tier, sticky-session design)
`app/Shared.py`'s `GAME_SESSIONS` dict is a per-worker in-memory cache — `_get_session()` reads memory → Redis → DB (`PlayerState` table) in that order and backfills upper tiers on a hit. `_persist_session()` write-throughs to Redis + DB on every mutating (non-GET) request via the `after_request` hook in `app/__init__.py`. Only `player`/`inventory`/`map`/`chapter`/`gold`/turn counters are serialized — `battle` (the live `BattleSession`) and `hook` (`BalanceHook`) are deliberately **not** persisted; recovering a session after a worker restart always reconstructs with `battle=None`, so any in-progress fight is lost and must be restarted (the frontend's `battleAction()` in `Actions.js` handles the resulting 400 by resyncing to the map instead of retrying). This whole design assumes sticky sessions (same user → same worker) and a single gunicorn worker; scaling workers safely would need this design revisited, not just a `--workers` bump.

Even within one worker, `--threads 8` means multiple requests for the *same* user can run concurrently. `app/Shared.py` keeps a per-uid `threading.Lock` registry (`_get_user_lock()`), wired into `app/__init__.py`'s `before_request`/`teardown_request` (skipped for GET, which never mutates) so all of a given uid's mutating requests are serialized — added after this exact race let a duplicated `/api/rest` call double-grant exp and let a battle step double-execute. A request that can't acquire its uid's lock within 8s gets a 423 instead of hanging. `GAME_SESSIONS` also isn't unbounded: `_get_session()` evicts entries idle for over an hour from the in-memory tier only (checked at most every 5 minutes) — an evicted session reconstructs from Redis/DB on the next request exactly like the worker-restart path above, with the same `battle=None` trade-off.

### Inventory swap tickets (`pending_swaps`)
Every "your bag is full, pick something to drop" flow — shop purchases, event item finds, battle-reward overflow (including the mid-boss's guaranteed potion) — funnels through one endpoint, `POST /api/inventory/swap` (`app/Inventory.py`), rendered by one shared modal (`#modal-item-inventory`, `static/js/UI_Player.js`'s `refreshItemModal()` in `overflow` mode — see "Frontend: no build step" below). The item a client claims it's owed is never trusted directly: the producing call sites (`app/Map.py`'s `shop_buy()`/`_event_item_found()`, `app/Battle.py`'s `_finish_battle()`) register a one-time ticket via `app/Shared.py`'s `_register_pending_swap(gs, item, source, price=0)` the moment a slot turns out to be full — this generates and returns an unguessable `ticket_id`, which is what the client must send back (not the item name; two simultaneous tickets for the same item, e.g. one paid shop purchase and one free reward, would otherwise be indistinguishable). `_pop_pending_swap(gs, ticket_id)` consumes a ticket by that id; `_restore_pending_swap(gs, ticket)` puts an already-popped ticket back (same id) when a swap attempt fails partway (insufficient gold, slot mismatch, or the drop itself failing), so the client can retry with the ticket it's already holding. A shop-sourced ticket carries its price and is charged at swap *confirmation*, not at the original purchase attempt. `POST /api/inventory/swap/cancel` voids a ticket the player declines, so it doesn't linger forever. Tickets ride in the Redis-backed session snapshot (`_snapshot_dict()`/`_gs_from_snapshot()`) but have no dedicated DB column — same durability tier as `battle`, lost only if both Redis and the in-memory tier are gone. The swap request itself is `{ticket_id, drops: {item_name: count, ...}}` — `game/Inventory.py`'s `discard_multi()` validates every requested count against actual holdings *before* removing anything (atomic, no partial-drop on a bad request), letting the player clear more than one stack in one confirm. A new "inventory full" producer needs to register a ticket the same way — don't let `inventory_swap()` trust a client-sent item id directly.

### Battle UI: live inventory sync + victory-screen persistence
`ai/battle_session/State.py`'s `_state()` (the per-turn battle response) includes a live `inventory` breakdown (`_live_inventory_dict()`, built from `self.items` the same way `app/Shared.py`'s `_player_dict()` falls back for a non-`Inventory` list) alongside the older flat `items` field — `static/js/UI_Battle.js`'s `syncPlayerBattleState()` copies both onto `state.player`. Before this, the player-panel item popup read `state.player.inventory`, which only `items` (not `inventory`) was updated for during a battle, so it could show stale counts mid-fight.

`static/js/UI_Battle.js`'s `updateBattleModeVisibility()` no longer force-hides `#battle-mode` the instant a battle's final response arrives (`bs.done`) — only `setMapMode()` (`static/js/UI_Map.js`, called from `handleMapNodeDone()` well after the reward modal, any inventory-overflow swaps, and level-up stat allocation have all resolved) does that now. This keeps the final battle scene (dead enemy, victory pose) visible — blurred behind the reward/level-up modals, not blacked out — until the player has actually clicked through them. `static/js/RewardModal.js`/`StatAllocate.js`'s `showRewardModal()`/`openStatAllocate()` are both promise-based (resolve when their modal closes) specifically so `static/js/Actions.js`'s `battleAction()` can `await` them in a fixed order (reward → overflow swaps → stat allocation → map return) instead of firing the stat modal immediately and racing the reward modal.

### Redis fallback (`core/RedisCache.py`)
Redis is strictly a second-tier cache in front of the DB, never the source of truth. If `REDIS_URL` is unset, every `redis_get`/`redis_set` call is a silent no-op and the game runs on DB-only persistence with no behavior change — local dev normally has no Redis at all. If it *is* set, `_get_client()` connects lazily on first use and, once connected, reuses that client for the worker's lifetime; a failed connection attempt doesn't disable Redis permanently, it retries after a 30s cooldown (the earlier version cached "already tried" before the attempt even completed, so one transient failure at boot silently killed Redis for that worker's whole life). Every `redis_get`/`redis_set` call also individually try/excepts and falls back to `None`/no-op on any runtime error — a mid-life Redis outage degrades to DB-only, it doesn't 500.

### Frontend: no build step
`static/js/*.js` are plain scripts loaded via `<script>` tags in `static/index.html`, in dependency order (`Api.js` → `State.js` → `CharSprite.js` → `BattleSequencer.js` → … → `Main.js` last). There is no bundler and no module system — everything is global-scope. Adding a new JS file means inserting a `<script>` tag at the correct position in that load order (before its first caller, after anything it depends on), not just dropping the file in `static/js/`.

`CharSprite.js` drives sprite-sheet battle animations (`setCharState`); `State.js`'s `CHAR_IMAGES` table maps each character/state to either a static PNG path or a `{src, type:'sheet', frames, fps, loop}` descriptor. `BattleSequencer.js` derives actual animation wait-times from `frames/fps` rather than fixed constants — keep it that way when adding new sheets so timing doesn't drift from what's actually on screen.

`static/css/battle/BattleStage.css`'s `.battle-stage` is always a 5-column CSS grid (`.battle-slot` × 5: player, gap, up to 3 enemy slots) whose height is one shared `--battle-stage-h` variable (currently 383px, `--battle-slot-h` derived from it) applied uniformly regardless of battle type. `static/js/battle/BattleRender.js`'s `renderEnemySlots()` only ever hides the *inner* `#enemy-slot-N` combatant for an unused enemy slot — the outer `.battle-slot` grid item is never removed by JS. That's harmless at 5 columns (an empty item just occupies an empty column), but `.battle-stage.is-boss` narrows the grid to 3 explicit column tracks (`1fr 1fr 3fr`) for boss fights (always solo) — with 5 grid items still present, the 2 unused ones wrapped onto an implicit second row, silently doubling the stage's rendered height. `.battle-stage.is-boss > .battle-slot:nth-child(4)`/`:nth-child(5)` now hard-hide those two grid items outright when boss mode is on. If a future change makes elite/boss fights ever have 2+ enemies, this nth-child rule needs revisiting.

### Balance-curve stacking (read before touching monster stats)
Enemy stats going into a fight are the product of **four independently-defined multipliers**, spread across two files: `GRADE_MULT` (하/중/상) and `_level_curve_mult()` (per-level scaling) in `game/Enemy_Class.py`'s shared `_apply_grade()`, then `STAT_SCALE`/`ELITE_STAT_SCALE` (multi-enemy discount) and `_early_game_multi_scale()` (extra early-level dampener) in `app/Map.py`. Both files cross-reference each other in comments precisely because no single function reasons about the combined effect. This combination was tuned empirically against `TestFile/montecarlo.py`-style full sweeps (all monsters × levels 1–25 × all jobs) to hit a target win-rate band — changing any one multiplier in isolation risks re-breaking that balance; re-run a full sweep after any change here, don't eyeball it. Boss factories (`Make_MidBoss`/`Make_FinalBoss`) intentionally bypass `_apply_grade()` and are tuned directly.

### Elemental system
`ai/battle/Elements.py`'s `ELEMENT_IMMUNITY_BY_ENEMY_TYPE` + `is_element_immune()` gate elemental damage; `ai/Auto_AI.py`'s skill-scoring must check immunity before ranking a skill (an AI that ignores this will repeatedly pick a 0-damage move against an immune target instead of falling back).

### Elite monster patterns (`ai/battle/EliteKit.py` + `ai/battle_session/Elite_Actions.py`)
Elite nodes spawn one `elite_leader`-flagged `EntitySnapshot` (chosen from `app/Map.py`'s `ELITE_CHAPTER_POOL[chapter]`) plus, for non-solo-only/non-pair-only types, an undecorated hard-grade escort from the normal `CHAPTER_TIER_POOL` — only the leader gets a pattern. `EliteKit.py` holds the numeric constants and `elite_forced_action()`, an override checked at the top of `EnemyAI.decide()` (`ai/Auto_AI.py`) for leaders whose pattern is "force this specific skill on the trigger turn" (bat, assassin, fire/lightning slime) — it resets its own trigger counter/phase before returning so the next cycle starts clean. Leaders with a full state machine instead of a single forced action (golem's 3-phase cycle, the priest's revival ritual) bypass `EnemyAI` entirely via a dedicated branch in `ai/battle_session/Enemy_Actions.py`'s `_single_enemy_action()`, the same place that already special-cases plain priests. Where an elite pattern's effect maps onto something the engine already does, it reuses that mechanism rather than adding a parallel one: the fire/lightning slimes' stack-reset rides the existing `REACTIONS["overload"]` entry and the ice slime's armor-break rides the existing physical-vs-ice "shatter" branch, both in `apply_element_and_react()`; the golem casts the real monster-tier `수비태세2`/`몸통박치기2` (`MONSTER_SKILL_META`, weaker than the player's own versions) rather than reimplementing them. Split/revived enemies are marked `reward_eligible=False`, which `app/Battle.py`'s `_get_defeated_list()` filters out of both exp and gold/item calculation. Known limitation: the design intent that a real battle and a Monte Carlo simulation given the same RNG seed produce identical results does **not** hold for elites (or in general) — `ai/battle_session/*` and `ai/battle/Engine.py` run two different action-orchestration code paths today, only the damage/skill leaf functions are actually shared.

### Automatic monster balancing (`ai/Simulator.py` + `core/Balance_Hook.py`)
Every time a player first meets a monster type (or levels up, which invalidates the cache), `BalanceHook.get_enemy()` submits a `MonsterFactory.generate_all()` job to `_SIM_EXECUTOR`, a small process-wide pool of 4 daemon worker threads (`_BoundedDaemonPool`, not stdlib `ThreadPoolExecutor` — see below) fed by a `queue.Queue`. That constructs a `StatTuner`, whose `power_index = PlayerPowerIndex.calc(player)` (0.4–2.0, derived from HP/MP ratio, skill/potion inventory, raw stats, SPD) shifts the target win-rate, then `StatTuner.tune()` binary-searches (≤20 iterations, 300–500 simulated `BattleEngine` fights per iteration via `BattleSimulator`) a stat-scale multiplier until the simulated win rate lands within tolerance. This is a real, live automatic-balancing pipeline — it is not the same layer as the hand-tuned `GRADE_MULT`/`_level_curve_mult`/`STAT_SCALE` multipliers described above; both stack on the same enemy.

These jobs run on whichever of the 4 workers picks them up and can't be cancelled once queued, so a level-up can't stop one already in flight. `BalanceHook._sim_generation` guards against a stale job overwriting the fresh post-levelup cache when it eventually finishes — each job captures its generation number at submit time and only writes to `_monster_cache` if that still matches `self._sim_generation` when it completes; `on_level_up()` bumps the counter, so every in-flight job from before the level-up becomes a silent no-op. Because `_SIM_EXECUTOR` has exactly 4 worker threads process-wide (shared across every `BalanceHook` instance) and jobs are *submitted* to its queue rather than each getting its own freshly-spawned thread, repeated "new game" clicks or several players meeting a new monster at once queue up extra work instead of spawning unbounded OS threads — the earlier version used a raw `threading.Thread(daemon=True)` per job plus a `threading.Semaphore(4)` that only capped concurrent *execution*, not thread *creation*, so a burst of requests could still pile up an unbounded number of threads blocked on the semaphore. `_BoundedDaemonPool` is hand-rolled rather than `concurrent.futures.ThreadPoolExecutor` specifically because that stdlib pool's worker threads are non-daemon — an `atexit` hook it registers blocks interpreter/process shutdown until every queued job drains, which would make gunicorn worker restarts wait on in-flight balance simulations; this module's daemon-thread design intentionally guarantees simulations never delay server shutdown.

### Post-battle feedback pipeline (`app/Battle.py` → `core/Balance_Hook.py` → `ai/FeedBack.py`)
On a real defeat, `app/Battle.py`'s `_finish_battle()` calls `battle.to_battle_result()` (a `BattleSession` method in `ai/battle_session/Rewards.py`) to turn the turn log into a `BattleResult`, then `gs["hook"].after_battle(result)`. That runs `ai/BehaviorAnalyzer.py` (play-style classification) and `ai/FeedBack.py`'s `RuleBasedAnalyzer` (rule-based post-battle report: headline/good plays/bad plays/suggestions/score, compared against `BalanceHook`'s last cached AI-vs-same-monster simulation) and returns a `FeedbackReport`. `_finish_battle()` attaches it to the API response as `result["feedback"]`; the frontend's `showGameOver(feedback)` (`static/js/map/MapChapter.js`) renders it on the game-over overlay, escaped through `escapeHtml()` since the analyzer's text can echo the player's own chosen name. Known limitation: `sim_result` is a 1v1 comparison even for multi-enemy fights, so the "AI comparison" feedback line is approximate there — the module was designed 1v1-first.

### Server-side error visibility (`core/ErrorLog.py`)
Every server-side failure used to be a bare `print()` — invisible unless someone opened the Render console. `log_error(context, exc)` is now the standard way to report a caught exception: it prints (unchanged local-dev behavior), best-effort writes an `ErrorLog` row to the DB, and best-effort POSTs to `ERROR_WEBHOOK_URL` (Discord-compatible) if that env var is set — all three steps degrade gracefully on their own failure, matching the `RedisCache.py`/`SECRET_KEY` fallback pattern elsewhere in this codebase. `app/__init__.py` also registers a global `@app.errorhandler(Exception)` as the last-resort catch for anything no route's own try/except caught; it must re-raise/pass through `werkzeug.exceptions.HTTPException` unchanged (404s etc. are also `Exception` subclasses) or every routine 404 becomes a logged 500. There is no admin web page for these logs — this app has no login/authorization system at all, so exposing them over HTTP would itself be a new hole. Read them with `python3 scripts/view_errors.py` (point `DATABASE_URL` at the production DB to check live errors).

### Master mode (`app/Master.py`, local-only debug shortcuts)
A floating panel (`static/js/MasterMode.js`, hidden unless `/api/master/status` returns 200) with buttons for instant level-ups, HP/MP full heal, and jumping straight into a boss/elite/specific-monster fight without walking the node map — built for fast balance/pattern iteration. Gated in `app/__init__.py`: `MASTER_MODE=1` must be set **and** the `RENDER` env var (auto-injected by Render) must be absent, so setting `MASTER_MODE=1` on Render by mistake still can't turn it on — when the check fails, `app/Master.py` isn't even imported, so the routes don't exist (404, not 403). Its battle-start endpoints reuse `app/Battle.py`'s `_start_battle()`/`_start_battle_multi()` and `app/Map.py`'s `_make_elite_encounter()` directly (same balance pipeline, same spawn rules as a real node) but leave `gs["pending_node_id"]` unset, so `_finish_battle()`'s node-completion branch never fires — rewards still pay out on victory, but no map node gets marked visited.

## Development & verification checklist

A change isn't done because it rendered correctly once — treat it as complete only once these hold, and say so explicitly in whatever you report back (what you tested, what you didn't, and any lifecycle/concurrency/security angle the change touches — every commit message on this branch already does this; keep doing it).

**Never trust client input for anything the server already knows authoritatively** — price, node/item identity, "which reward am I owed," turn/battle state. Recompute or validate it server-side from `gs`/the DB instead. This isn't a hypothetical: `app/Map.py`'s `shop_buy()` and `map_node_complete()`, `game/Map.py`'s `mark_visited()`, and `app/Inventory.py`'s `inventory_swap()` all shipped with exactly this bug and were fixed later (`e072e39`, `7485ed9`) — reintroducing it in a new endpoint is a repeat, not a new discovery.

**Naming.** This codebase is mostly Python `snake_case` / JS `camelCase`, but it is not uniform on purpose: `game/Enemy_Class.py`'s entity factories (`Make_Goblin`, `Make_FinalBoss`, …) and a couple of `game/Lv.py` methods (`Lv_up`, `Get_exp`) intentionally use a different case convention and are referenced by name across `core/Balance_Hook.py`, `app/Map.py`, and most of `TestFile/` — match whatever convention the file you're editing already uses rather than "fixing" these; a drive-by rename breaks every call site. File/import case must match exactly regardless of style (see "Backend layering" above) — a mismatch works on case-insensitive macOS and 404s on Render's case-sensitive Linux, which has happened for real (`8b6013c`).

**Don't give a Python function a mutable default argument** (`def f(x=[]): ...`) — use `None` and initialize inside the body.

**Before calling something done:**
```bash
python3 -m compileall App.py app DB ai core game    # syntax
for f in TestFile/test_*.py; do python3 "$f"; done   # full regression suite (see Commands above)
git status --short && git ls-files static             # a new image/js/css file that isn't
                                                        # `git add`-ed works locally and is
                                                        # simply missing on Render
python3 -c "from app import create_app; create_app(); print('APP_OK')"
```
There's no Node.js in this environment, so there's no automated JS syntax check to run — proofread changed `.js` files directly, or verify behavior via a live browser check (this session's Browser-pane tools) instead of assuming a `node --check`-equivalent exists. Skip any check that would touch the local DB/log files/images if the user asked for a read-only review, and say what you skipped and why.

A dedicated code-review pass (correctness, dead code, simplification — the `code-review` skill) covers deeper line-by-line auditing; the above is the baseline every change should clear before that.
